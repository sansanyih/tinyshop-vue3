## 一、简历里怎么写（可直接复制）

### 项目名

**小蜂商城 · uni-app 跨端商城（开源项目重构）**
`技术栈：uni-app + Vue3 + TypeScript + Vite + Pinia + SCSS`

### 一句话简介

基于 Apache-2.0 开源商城 TinyShop-UniApp（Vue2 + webpack）做架构级重构，迁移到 uni-app + Vue3 + TS + Vite + Pinia，并自建 Mock 层实现无后端完整交易闭环，同时产出 H5 与微信小程序双端产物。

### 项目要点（选 4 条放简历，字数都不长）

1. **技术栈迁移**：将开源商城从 Vue2 选项式 + vue-cli/webpack 重构为 `uni-app + Vue3 组合式 + TypeScript + Vite + Pinia`，独立重写 10 个页面与 6 个通用组件（4480 行 Vue/TS），`vue-tsc` 严格类型检查 **0 error**。
2. **请求层 + Mock 双通道**：基于 `uni.request` 封装拦截器（Token 注入 / 401 清登录态并带 `redirect` 回跳 / loading 引用计数 / 业务错误统一兜底），并实现按 url 匹配的 Mock 层，**不启动后端即可跑通「商品 → SKU 选规格 → 购物车 → 下单 → 支付 → 订单」全链路**。
3. **分包与体积治理**：按业务域拆分 `order` / `account` 两个子包并配置 `preloadRule` 预加载；小程序主包 **629KB**、子包 **13.4KB / 11KB**，远低于 2MB 限制；H5 生产构建 **15.8s**，首屏 JS **259KB（gzip 94KB）**。
4. **组件化与体验优化**：抽象 `RfNavbar`（自定义导航栏，适配状态栏/小程序胶囊）、`RfProductCard`（瀑布流/列表双布局）、`RfSkeleton`（骨架屏）、`RfNumberBox` 等通用组件；商品图固定比例 + 懒加载，消除首屏跳动。
5. **工程化**：多端构建脚本、基于 CDP 的移动端截图脚本（`npm run shots` 一键生成视觉回归图）、GitHub Actions 自动构建并部署 H5。

## 二、面试被追问怎么答

### Q1：这个项目是你自己从零写的吗？

> 不是，是重构。业务原型来自 Apache-2.0 开源项目 TinyShop-UniApp（1.8k star，Vue2 + webpack）。
> 我做的事是把它整体迁到 Vue3 + TS + Vite + Pinia，重写了请求层、状态层、Mock 层和分包方案，页面和组件全部重写。
> README 里有原作者和许可证声明。

**为什么这么答**：面试官一搜就知道，坦诚反而加分；而且「迁移重构」本身就是比「再写一个商城」更稀缺的能力项。

### Q2：为什么要重构它？收益怎么衡量？

> 三个目的：补齐小程序/跨端经验；练一次真实项目的迁移（Vue2→Vue3 是现在大量存量项目的刚需）；验证自己对工程化的理解。
> 收益我拿三个指标衡量：构建方式从 webpack 4 换到 Vite，冷启动构建 15.8s；类型从「没有」到 `vue-tsc` 0 error；包体积靠分包压在小程序 2MB 限制内。

### Q3：迁移过程中最难的地方？

> 三个坑：
> 1. 原项目依赖 `node-sass@4`，它只支持到 Node 12/13，在 Node 22 上直接编译失败——换成 dart-sass，并处理 webpack 4 在 Node 17+ 需要的 `--openssl-legacy-provider`。
> 2. Vue2 的 mixin + Vuex 状态耦合很深，迁移时不是逐行翻译，而是按「领域」重新切成 user / cart / app 三个 Pinia store，把共享逻辑沉到 composable。
> 3. 请求层原来和 store、storage 互相引用，我按「api 定义 / 请求封装 / 状态」三层重写，把 401 处理集中到拦截器里。

### Q4：为什么这么拆分包？preloadRule 是干吗的？

> 按业务域拆：`order`（确认订单、订单列表）和 `account`（登录、地址）都是低频路径，放子包能保住主包体积；
> `preloadRule` 让用户在购物车/我的页面空闲时预加载对应子包，点进去时不用等下载。主包只留首页、分类、详情、购物车这些高频路径。

### Q5：401 并发怎么处理？现在这套够用吗？

> 当前实现是：401 → 清登录态 → 带 `redirect` 跳登录 → 登录后回跳原页面（tabBar 页走 `switchTab`，普通页走 `redirectTo`）。
> 不足是：如果同时有 3 个请求 401，会重复触发跳转。改进方案是加一个刷新锁 + 请求队列：首个 401 触发 refreshToken，其余请求挂起，刷新完成后重放；refresh 本身失败才登出。这个我在原项目里见过类似实现（`isRefreshing` + `requests` 队列），准备补到当前版本。

### Q6：Mock 层和真后端怎么切？会不会忘了关？

> 用环境变量 `VITE_API_BASE` 控制：不配置就走 Mock，配置就走真实 `uni.request`，业务代码零改动。
> 上线构建时用 `.env.production` 显式配置真实地址，CI 里也做了类型检查；同时 Mock 只在前端入口判断一次（`isMockEnabled()`），不会散落在业务代码里。

### Q7：为什么不用 uView / uni-ui？

> 这个项目只用了 6 类组件，引一整套 UI 库反而会把包体积和样式覆盖成本带上来；
> 我选择自己写 `Rf*` 组件，样式用 SCSS token（`uni.scss`）统一，后续要接 UI 库也只是替换实现层。
> 如果项目页面更多、需要表单/日历等复杂组件，我会优先选 uni-ui（官方维护、与 uni-app 版本同步）。

### Q8：首屏做了什么优化？

> - 骨架屏：列表首屏不白屏，数据回来后替换
> - 图片固定占位比例 + `lazy-load`，避免图片加载造成布局抖动
> - 公共数据（分类/公告/Banner）用 `app` store 做一次性加载 + `ready` 标记，tab 来回切不重复请求
> - 商品列表分页 + 触底追加，不做一次性长列表渲染
> - 首屏 JS gzip 94KB，尚未做路由级懒加载以外的进一步拆分，这是下一步的优化点

### Q9：如果要上 App 端，要注意什么？

> - 条件编译：`#ifdef APP-PLUS` 处理 plus API、权限、状态栏高度
> - 自定义导航栏要处理刘海屏安全区（我现在的 `RfNavbar` 已用 `statusBarHeight` + `safe-area-inset-bottom`）
> - H5 用的 `hash` 路由在 App 端可以保留；但 App 端首屏要用 `app-plus` 的 splash 配置
> - 原生能力（支付、推送）要走 `uni.requestPayment` / 第三方 SDK，不能沿用 H5 方案

### Q10：这套架构现在还有什么不足？

> 诚实说 4 点：
> 1. 没有单元测试，只有截图回归；下一步用 Vitest 给 store 和 utils 补用例
> 2. 没有错误监控，线上白屏只能靠用户反馈；计划接 Sentry 或自建上报
> 3. 图片还是本地 JPG，真上线会转 webp + CDN + 响应式尺寸
> 4. 只迁了核心 10 页，原项目其余页面（评价、优惠券、发票）按需追加
